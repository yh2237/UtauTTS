# Qt WebAssembly版の構成

## 1. 処理フローとスレッド分担

```text
Main Thread (Qt / UI)               Web Worker (Go / DSP / Synthesis)
┌─────────────────────────┐         ┌─────────────────────────┐
│ Main.qml                │         │ Go Engine (Wasm)        │
│   ↓                     │         │   ↓                     │
│ Backend::callAsync      │──Post──>│ engine-worker.js        │
│   ↓                     │         │   ↓                     │
│ engine-loader.js        │<──Done──│ 音声合成 / 特徴量計算   │
│   ↓                     │         │   ↓                     │
│ FSミラー同期            │         │ 仮想FSへの書き込み      │
│   ↓                     │         └─────────────────────────┘
│ HTML5 Audio再生 / QML   │
└─────────────────────────┘
```

- メインスレッド: QMLの描画、UI操作、HTML5 Audioでの再生と、Qtが読むファイルシステム（FS）ミラーを受け持ちます。
- Web Worker: Goの合成エンジン、Open JTalk、WORLD、音響モデル、音源キャッシュ、波形生成を受け持ちます。重い音声処理でUI描画が止まらないように分けています。

---

## 2. リモート音源のオンデマンド読み込み

ボイスバンクは全体の容量が大きいため、起動時にすべてのWAVをダウンロードしません。
1. 起動時は音源マニフェストからファイル一覧のみ取得し、`oto.ini` などの各ファイルは読み込み時に取得します。
2. 合成の前に、その文の原音候補WAVだけを最大8並列で事前取得して仮想FSへ配置します。

---

## 3. 状態管理と非同期の整合性

- 発話IDと変更番号: 解析や合成の結果はUIの行番号ではなく、発話ごとのIDと変更番号に紐付けて管理します。続けて編集しても、古い合成結果で最新のUI状態が上書きされません。
- ファイルの同期: Workerは呼び出し前後でファイルの更新番号を比較し、Worker内で書き出したWAVなどのファイルをメインスレッドのFSミラーへコピーします。これによりQtからファイルを同期的に読めます。

## 4. 参照照合の推論

参照照合の重い処理（KokoroとWavLM）はGoのWasmではなくONNX Runtime Webで動かします。

- 推論用のWorkerはページ側で作成し、エンジンのWorkerとはMessagePortで接続します（エンジンのWorker内で推論を動かすと合成の途中で応答しなくなるため）。
- エンジンは推論が必要なとき `{ok: false, need: [...]}` を返します。ページ側がONNXで計算し結果を `provideInference` で渡すと、エンジンが同じ呼び出しを再実行します（最大8回）。GoのWasmからはJavaScriptのPromiseを待てないため、この往復で処理します。
- モデルは使う言語の分だけ初回利用時にダウンロードし、Cache Storage（`utautts-reference-v1`）に保存します。英語・スペイン語・ポルトガル語で約310MB、中国語で約210MBです。
- 推論のスレッド数は、cross-origin isolation（COOP/COEP）があるページで最大8、ないページで1です。
- 作成した索引はCache Storage（`utautts-reference-index-v1`）に保存し、次に開いたときに復元します。
